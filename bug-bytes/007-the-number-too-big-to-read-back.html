the number too big to read back

github.com/k8snetworkplumbingwg/whereabouts · PR #760

🐣 first — how does Whereabouts track IPv6 addresses?

Whereabouts stores IP assignments as offsets from a base address.
For IPv6 /64 subnets, offsets can be huge numbers —
up to 18.4 quintillion (2⁶⁴ − 1).
The offset is written as a string and read back when releasing IPs.

🐛 one problem found

1. 🔴 write unsigned, read signed — half the range is invisible
The write path stores offsets as uint64 (max 18.4×10¹⁸).
The read path parses them as int64 (max 9.2×10¹⁸).

Any offset above 9.2×10¹⁸ silently fails to parse.
The old IP is never freed → new pod gets same IP →
kernel rejects duplicate (DADFAILED) → pod stuck forever in FailedCreatePodSandBox

💭 what changed?

before fix

write: uint64 → "12345678901234567890"
↓
read: ParseInt(s, 10, 64)
↓
> 9.2×10¹⁸? → parse error
↓
allocation invisible
↓
IP never freed → DADFAILED 💀

after fix

write: uint64 → "12345678901234567890"
↓
read: ParseUint(s, 10, 64)
↓
full range decoded ✓
↓
IP freed on pod delete
↓
new pod gets clean address ✓

💡 the rule

the write path and read path must agree on the type.
If you serialize as unsigned, you must deserialize as unsigned.
A mismatch doesn't crash — it silently halves your range,
and the data you can't read back becomes a ghost that haunts you.
